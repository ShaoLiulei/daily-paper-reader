## 摘要
使用合成推理数据训练大语言模型（LLMs）已成为增强其推理能力的流行方法，而影响这一范式有效性的关键因素是生成的逐步推理数据的质量。为了生成高质量的推理数据，许多近期的方法生成合成推理路径并根据最终答案的正确性进行过滤，这往往忽略了中间推理步骤中的缺陷。为了加强对中间推理步骤的验证，先前的工作主要求助于代码执行或符号推理引擎。然而，基于代码的验证仅限于代码或数学任务，而推理引擎需要结构良好且完整的上下文。因此，现有方法在涉及模糊或不完整上下文的自然语言推理任务中无法有效发挥作用。在这些任务中，合成数据仍然缺乏验证每个推理步骤的可靠检查。为了应对这一挑战，我们引入了 ORACLE，这是一个受三段论推理启发的结构化数据生成框架。ORACLE 将 LLM 的生成优势与符号监督相结合：LLM 生成逐步推理上下文，而符号推理引擎验证每个中间步骤的有效性。通过采用统一的提示模板来诱导模块化推理链，ORACLE 实现了细粒度的步骤级验证，促进了高质量多步推理数据的构建。在六个逻辑、事实和常识推理基准测试中，我们的 ORACLE 在多个模型上始终优于强大的基准线。

## Abstract
Training large language models (LLMs) with synthetic reasoning data has become a popular approach to enhancing their reasoning capabilities, while a key factor influencing the effectiveness of this paradigm is the quality of the generated multi-step reasoning data. To generate high-quality reasoning data, many recent methods generate synthetic reasoning paths and filter them based on final answer correctness, often overlooking flaws in intermediate reasoning steps. To enhance the verification of intermediate reasoning steps, prior work primarily resorts to code execution or symbolic reasoning engines. However, code-based validation is restricted to code or mathematical tasks, and reasoning engines require a well-structured and complete context. As a result, existing methods fail to function effectively in natural language reasoning tasks that involve ambiguous or incomplete contexts. In these tasks, synthetic data still lack reliable checks for verifying each reasoning step. To address this challenge, we introduce ORACLE, a structured data generation framework inspired by syllogistic reasoning. ORACLE integrates the generative strengths of LLMs with symbolic supervision: the LLM produces step-wise reasoning contexts, while a symbolic reasoning engine verifies the validity of each intermediate step. By employing a unified prompting template to elicit modular reasoning chains, ORACLE enables fine-grained, step-level validation, facilitating the construction of high-quality multi-step reasoning data. Across six logical, factual, and commonsense reasoning benchmarks, our ORACLE consistently outperforms strong baselines on multiple models.

*   **研究背景**：目前主流方法（如 RFT、STaR）主要通过“最终答案正确性”来过滤合成数据。然而，模型可能通过错误的逻辑或捷径（Shortcuts）偶然得到正确答案。

    *   **代码验证**：仅限于数学或编程任务。
    *   **符号推理引擎**：虽然精确，但对自然语言的模糊性和上下文缺失非常敏感，难以直接应用于开放域推理。
*   **研究目标**：提出一种受“三段论”启发的框架，将 LLM 的生成能力与符号引擎的严谨性结合，实现对自然语言推理步骤的细粒度验证。

### 2. 方法论（ORACLE 框架）
ORACLE 的核心思想是**“结构化模板 + 符号监督 + 束搜索（Beam Search）”**。

*   **结构化推理模板**：要求模型按模块生成推理步骤，包括：
    *   `<QUERY>`：当前步骤要解决的子问题。
    *   `<FACTS>`：所需的已知事实或前提。
    *   `<RULE>`：应用的逻辑规则。
    *   `<REVISION>`：自我反思与修正过程。
    *   `<REASONING_RESULT>`：得出的中间结论。
*   **两阶段训练流程**：
    1.  **第一阶段（格式内化）**：利用少量人工示例进行 Few-shot 提示，生成初步合成数据，通过格式和答案过滤后进行监督微调（SFT），使模型掌握结构化输出。
    2.  **第二阶段（符号增强）**：
        *   **Beam Search 引导生成**：在生成每一步时，利用 LLM 将自然语言翻译为符号语言，交由符号推理引擎（Pyke）执行。
        *   **综合评分机制**：根据引擎执行成功与否（$W_1$）、LLM 精度评估（$W_2$）和可行性评估（$W_3$）进行打分，筛选高质量路径。
        *   **数据产出**：收集正确路径用于 SFT；对比“引擎验证通过”与“验证失败”的兄弟节点，构建偏好对用于 **DPO（直接偏好优化）**。

### 6. 主要结论与发现
*   **性能领先**：ORACLE 在所有测试模型和数据集上均达到或接近最优性能，尤其在逻辑推理任务（如 ProofWriter）上提升显著（最高提升约 5.7%）。
*   **迭代增益**：随着训练迭代增加，模型生成可被符号引擎成功执行的步骤比例显著提升，说明模型不仅学会了推理，还学会了如何生成“规范化”的逻辑步骤。
*   **跨领域有效性**：即使在非严格逻辑任务（如常识推理）中，引入符号约束也能通过提升中间步骤的严谨性来最终改善答案准确率。

### 7. 优点与亮点
*   **细粒度验证**：突破了传统“仅看结果”的黑盒验证，实现了对推理过程的“步进式”监督。
*   **神经-符号结合**：巧妙利用 LLM 处理自然语言的灵活性和符号引擎处理逻辑的确定性，互补短板。
*   **可解释性强**：结构化模板使模型的推理路径清晰可见，便于人工审计和错误溯源。

### 8. 不足与局限
*   **翻译瓶颈**：实验显示，推理引擎失败的一大原因是 LLM 无法准确将自然语言翻译成符号语言（Translation Error），这限制了框架在极复杂语义场景下的表现。
*   **计算开销**：Beam Search 结合外部引擎调用，在数据生成阶段的计算成本显著高于普通的采样方法。
*   **领域依赖**：虽然在常识推理上有提升，但对于完全不具备逻辑推导性质（如纯直觉或纯联想类）的任务，该框架的适用性可能受限。
